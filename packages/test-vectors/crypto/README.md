# Cryptography vectors

This is the exact specification (bytes and order) of three things:

- the **mailbox encryption**,
- the **signature of requests to the mailbox server**,
- the **end-to-end mail between NightMail addresses**.

It also comes with known-answer vectors. They check that the two implementations agree:

- TypeScript: `packages/core-ts` (the server seals and verifies). It generates the mailbox, request and end-to-end vectors.
- Rust: the app core (it opens and signs; for end-to-end mail it also seals and verifies). It must reproduce them.

| File | Contents |
|---|---|
| `mailbox.json` | Key derivation, padding buckets, sealed envelopes, envelopes that open and envelopes that must fail |
| `request-auth.json` | Canonical encoding, valid signatures, signatures that must be rejected, non-canonical requests, time window |
| `keys.json` | BIP39 phrase → `master`, outputs of each derivation label (with the address public keys), seed files (§3) |
| `name-cipher.json` | `nameCipher` values sealed with a known nonce, and those that must fail (§3.4) |
| `e2e-mail.json` | End-to-end mail: payload, signature and envelope of each vector, mails that open with the sender not verified, mails that do not open and mails that cannot be built (§4) |

`keys.json` and `name-cipher.json` do not come from `packages/core-ts`, because the server neither derives keys nor reads names. They are generated by `gen-keys.mjs` with `node:crypto` only, independently of the Rust core (see §3.5).

Conventions: bytes are **lowercase hex without `0x`**. Integers are **big-endian**. `‖` is concatenation. Secret keys are always the 32-byte seed (RFC 7748 and RFC 8032), never expanded formats.

**Regenerating.** Do this only on purpose, when the format changes. Each file has one generator:

| Files | Generate (write) | Check (no write) |
|---|---|---|
| `mailbox.json`, `request-auth.json`, `e2e-mail.json` | `npm run vectors` in `packages/core-ts` (runs `node scripts/vectors.ts`) | `npm test` in `packages/core-ts`: `test/vectors.test.ts` fails if the code no longer reproduces the stored files |
| `keys.json`, `name-cipher.json` | `node packages/test-vectors/crypto/gen-keys.mjs` from the repository root (Node ≥ 24.7) | the same command with `--check`: it writes nothing and exits with 1 if the stored files differ |

**Rust side.** The app core replays every file in its unit tests. They read the JSON files from this folder. From `apps/desktop/src-tauri`:

```
cargo test --lib -- crypto::tests keys::tests mail::e2e::tests mail::sync::e2e_tests::the_shared_vectors_open_and_verify_through_sync orchestrator::directory::tests::the_resolved_sender_verifies_the_vector_mail
```

- `crypto::tests`: `mailbox.json`, `request-auth.json`, `name-cipher.json`.
- `keys::tests`: `keys.json`.
- `mail::e2e::tests`: `e2e-mail.json`.
- `mail::sync::e2e_tests::the_shared_vectors_open_and_verify_through_sync`: `e2e-mail.json`, through the whole receive path.
- `orchestrator::directory::tests::the_resolved_sender_verifies_the_vector_mail`: `e2e-mail.json`, with its `directory` registered and the sender looked up through the real sender resolver.

## 1. Mailbox encryption (`nightmail:mailbox:v1`)

It follows the `InboxEntry` format of [MIP-0012 §6.4](https://github.com/midnightntwrk/midnight-improvement-proposals/blob/main/mips/mip-0012-native-asset-custody.md): ephemeral X25519 + HKDF-SHA256 + AES-256-GCM, with the same header and the same field order. The MIP encrypts a fixed 80 bytes. Here the message is a mail of variable length, so there are some differences:

| | MIP-0012 §6.4 | NightMail |
|---|---|---|
| Domain (HKDF `info`) | `midnight:custody:inbox:v1` | `nightmail:mailbox:v1` ‖ ephemeral pk ‖ recipient pk |
| Plaintext | fixed 80 bytes | length (u32) ‖ message ‖ zeros up to the bucket |
| Padding | 50 zero bytes **after** the ciphertext, not authenticated | **inside** the encryption: the real length is encrypted and authenticated |
| Envelope size | 192 bytes | 62 + bucket (power of 2 between 4 KiB and 32 MiB) |
| Low-order keys | not mentioned | rejected |

Adding both public keys to `info` (as HPKE does, RFC 9180) binds the encryption key to this ephemeral key and to this recipient. Replacing the ephemeral key in the envelope with an equivalent one makes the tag fail.

### 1.1 Envelope

| Offset | Length | Field |
|---|---|---|
| 0 | 1 | `version` = `0x01` |
| 1 | 1 | `suite` = `0x01` (X25519 + HKDF-SHA256 + AES-256-GCM) |
| 2 | 32 | ephemeral X25519 public key |
| 34 | 12 | AES-GCM nonce |
| 46 | 16 | AES-GCM tag |
| 62 | bucket | ciphertext (same length as the padded plaintext) |

Note: the tag comes **before** the ciphertext (as in the MIP). Many libraries return it after the ciphertext.

### 1.2 Key

```
shared = X25519(sk_ephemeral, pk_recipient)           (= X25519(sk_recipient, pk_ephemeral))
key    = HKDF-SHA256(ikm = shared,
                     salt = empty,                     (RFC 5869: same as 32 zero bytes)
                     info = "nightmail:mailbox:v1" (20 ASCII bytes) ‖ pk_ephemeral (32) ‖ pk_recipient (32),
                     L = 32)
AAD    = version ‖ suite                               (the first 2 bytes of the envelope: 01 01)
```

If `shared` is 32 zero bytes (a low-order public key), it is rejected. When sealing, this is a key error. When opening, the envelope is invalid.

**The public keys go into `info` as raw bytes**, so they must be canonical. X25519 ignores bit 255 and reduces modulo p (RFC 7748). A key with bit 255 set, or with `u ≥ p = 2^255 − 19`, gives the same `shared` as its canonical form, but a different `info` and a different `key`:

- **Sealing rejects a non-canonical `pk_recipient`** (bit 255 set, or `u ≥ p`: first byte ≥ `0xed`, the next 30 bytes `0xff` and the last one `0x7f`). Its owner computes `info` with the canonical key derived from their secret, and could not open the envelope. Vectors: `sealFailures.nonCanonicalRecipientPublicKeys`. The server drops such addresses before accepting mail (`isUsableMailboxPublicKey`: 32 bytes, canonical and not low order).
- **Opening needs no separate check.** `pk_ephemeral` is taken byte for byte from the envelope. If someone flips its bit 255, the tag is no longer valid (vector in `openFailures`). `pk_recipient` is always the one derived from the secret, which is canonical.

### 1.3 Bucket padding

```
padded = u32be(len(message)) ‖ message ‖ 0x00 … up to the bucket
bucket = the smallest power of 2 ≥ len(message) + 4, between 4096 and 33554432
```

- Buckets: 4096, 8192, 16384, …, 33554432 (14 values, in `constants.buckets`).
- Largest message: 33554428 bytes (`constants.maxPlaintextLength`). A larger one is not sealed.
- The **bucketed size** shown outside (for example, in the message list) is the size of the ciphertext: envelope length − 62.
- The **writer** fills the padding with zeros and always uses a bucket from the table.
- The **reader** only checks that `len ≤ len(padded) − 4`. It **ignores** the content of the padding and **does not require** the length to be a bucket from the table. This lets the table change without changing `version`.

### 1.4 Sealing (server; the app, for the end-to-end mail of §4)

0. Reject a `pk_recipient` that is not 32 bytes, canonical and not low order (1.2). Reject a message longer than 33554428 bytes.
1. `sk_ephemeral` = 32 fresh random bytes. `nonce` = 12 fresh random bytes. They are never reused.
2. `pk_ephemeral` = X25519(sk_ephemeral, base point).
3. `key` as in 1.2. `padded` as in 1.3.
4. `(ciphertext, tag)` = AES-256-GCM(key, nonce, AAD, padded).
5. Envelope = `01 01 ‖ pk_ephemeral ‖ nonce ‖ tag ‖ ciphertext`.

### 1.5 Opening (app)

1. Reject if the envelope is shorter than 62 bytes or **longer than 33554494 (62 + 32 MiB, `constants.maxEnvelopeLength`)**, or if `version ≠ 0x01` or `suite ≠ 0x01`.
   - The size limit is checked before allocating memory for decryption (and, when downloading, before reading the whole body). A malicious server cannot make the app allocate more than that. `openFailureOversized` is an envelope with a valid tag and one byte too many.
   - The `version` and `suite` check is mandatory even though the header is in the AAD. Anyone who knows the public key can build an envelope with another header and a valid tag for it (`openFailures` has two such vectors).
2. `shared` = X25519(sk_recipient, pk_ephemeral from the envelope). Reject if it is all zeros.
3. `key` as in 1.2, with `pk_recipient` = X25519(sk_recipient, base point).
4. Decrypt with AES-256-GCM (AAD = bytes 0 and 1 of the envelope). Reject if the tag is invalid.
5. Read `len` (u32be). Reject if the padded plaintext is shorter than 4 bytes or if `len > len(padded) − 4`. The message is the next `len` bytes.

**Every envelope rejection is the same error, with no detail** about which step failed. An envelope with an unknown `version` or `suite` is skipped, not interpreted. (A wrong-length secret key supplied by the app itself is not an envelope failure but a usage error.) After the message is copied out, the decrypted padded plaintext is wiped.

### 1.6 What is in `mailbox.json`

- `recipient`: the recipient key of all vectors.
- `kdf[]`: `sharedSecret`, `ephemeralPublicKey`, `recipientPublicKey` → `info` and `key` (the HKDF step only).
- `padding[]`: `plaintextLength` → `bucket` and `envelopeLength`, at the edges of each bucket.
- `seal[]`: deterministic sealing. With `ephemeralSecretKey`, `nonce` and the message, the result must be exactly the envelope.
  - The full envelope (`envelope`) is given for the small ones. `envelopeSha256` and `envelopeLength` are always given.
  - It includes the intermediate values `ephemeralPublicKey`, `sharedSecret` and `key`.
  - The message is `plaintext` (hex). If `plaintextPattern` is present instead, it is `plaintextLength` bytes where **byte `i` is `i mod 251`**.
  - There is one vector for the empty message and two per bucket edge (the largest that fits and the smallest that no longer fits).
- `open[]`: envelopes the reader must accept even though it would not write them this way (padding outside the table, padding with non-zero bytes) → `plaintext`.
- `openFailures[]`: `recipientSecretKey` + `envelope` that **must fail**:
  - altered tag, ciphertext, nonce or ephemeral key;
  - unknown version or suite (also with a valid tag for that header);
  - truncated envelope, or one with extra bytes;
  - another recipient key;
  - low-order ephemeral key, or one with bit 255 flipped;
  - low-order ephemeral key **with a valid tag** (the key comes from HKDF over the all-zero shared secret: only the check in step 2 of 1.5 rejects it);
  - valid tag with malformed padding.
- `openFailureOversized`: an envelope with a valid tag but 62 + 33554433 bytes long. It must be rejected for its length. It is not stored in full. Rebuild it by sealing, with `ephemeralSecretKey` and `nonce`, a padded plaintext of `paddedLength` zero bytes (without going through the bucket table). `envelopeSha256` confirms it is the same.
- `sealFailures`: the first length that can no longer be sealed (`plaintextLengthTooLarge`), and recipient keys that are not accepted: low order (`lowOrderRecipientPublicKeys`) and non-canonical (`nonCanonicalRecipientPublicKeys`).

The Rust core must, at least:

- reproduce `kdf`, `padding` and `seal` (sealing with the given ephemeral key and nonce; outside the tests, `seal_envelope` generates fresh ones for each envelope);
- open the `seal` vectors that have a full envelope, and the `open` vectors;
- reject all `openFailures` and `openFailureOversized`.

Notes for Rust. These vectors were fully reproduced by a test implementation written only from this document, with `x25519-dalek` 2.0.1 (feature `static_secrets`), `hkdf` 0.12.4, `sha2` 0.10.9 and `aes-gcm` 0.10.3:

- `x25519-dalek`: `StaticSecret::from([u8; 32])`, `PublicKey::from(&secret)`, `secret.diffie_hellman(&public)`, and `SharedSecret::was_contributory()` for the low-order rejection.
- `hkdf`: `Hkdf::<Sha256>::new(None, &shared)` (no salt) and `expand(&info, &mut key)`.
- `aes-gcm`: `Aes256Gcm` with a detached tag, `encrypt_in_place_detached` / `decrypt_in_place_detached`, because in the envelope the tag comes before the ciphertext.

## 2. Signature of mailbox requests (`nightmail:mailbox-api:v1`)

Every request to the mailbox API is signed with the address's **Ed25519** key. The signature is pure Ed25519 (RFC 8032, deterministic, 64 bytes) over this canonical encoding:

| Order | Field | Bytes |
|---|---|---|
| 1 | domain | `"nightmail:mailbox-api:v1"`, 24 ASCII bytes, no terminator |
| 2 | `host` | `u16be(length)` ‖ ASCII |
| 3 | `version` | 1 byte (currently `0x01`) |
| 4 | `method` | `u16be(length)` ‖ ASCII |
| 5 | `path` | `u16be(length)` ‖ ASCII |
| 6 | `addrKey` | 32 bytes |
| 7 | `timestamp` | `u64be`, Unix seconds |
| 8 | `nonce` | 16 random bytes, fresh for each request |

Variable-length fields carry their length in front, and the others have a fixed length. So two different requests never give the same bytes. `encodingExample` in the JSON breaks down the first vector field by field.

Field rules. Anything that breaks them **is neither signed nor verified**. Nothing is silently normalised.

| Field | Rule |
|---|---|
| `host` | 1–255 characters from `a-z 0-9 . - : [ ]`. It is the **authority of the server's configured base URL** (2.2), not the request's `Host` header. This stops a signature from being reused on another server |
| `version` | integer 0–255; the API version |
| `method` | 1–16 letters `A-Z` |
| `path` | starts with `/`; 1–2048 characters from `A-Z a-z 0-9 / . _ ~ % ? = & -`. **No `.` or `..` segments** in the part before `?`, including when the dots are written as `%2e` or `%2E` (`/a/../b`, `/a/%2e%2e/b`, `/a/.` are rejected; `/.well-known`, `/a..b` or `/a/...` are not). It is the request target **as sent, with its query string and not normalised** (`/v1/box/<addrKey>/messages?since=0`) |
| `addrKey` | exactly 32 bytes |
| `timestamp` | integer ≥ 0 (up to 2^53 − 1 in the TypeScript implementation) |
| `nonce` | exactly 16 bytes |

### 2.1 Signature verification (server)

1. Reject if the public key is not usable (`isUsableAuthPublicKey`): 32 bytes, canonical `y` and **not low order**. The low-order keys are the 14 encodings in `lowOrderPublicKeys`: 7 values of `y`, with and without the sign bit. With a low-order key, the trivial signature (`R` = identity, `S` = 0) is valid for one message in a few, and OpenSSL accepts it. The `invalid` vectors described as "low-order key" are requests where this happens. The server also drops such addresses when it syncs the registry.
2. Verify Ed25519 over the canonical encoding. Signatures whose length is not 64, and those with a non-canonical `S` (`S ≥ L`), are rejected.
3. Any malformed input (key, signature or field) gives "invalid signature", without throwing a different error.

### 2.2 HTTP transport

The request carries three headers. The rest of the signed message is already in the request itself or in the configuration:

```
GET /v1/box/621068aeef170d87aab62215f32c563c6ef3d198cf39b86a0fb109c4d2046c54/messages?since=0 HTTP/1.1
Host: nightmail.local
NightMail-Timestamp: 1794873600
NightMail-Nonce: c2c26fe8fbc2d23ec9d4be24bc44d0da
NightMail-Signature: c247b8f4747dd78be0037fcf80238ad3def1dd9b55fe324e37016883f48ab73b6dc3b70237acdf53ff7b72de4d57fd383082d451efd4fd26451f577847e4e308
```

(This is the first `valid` vector. Each vector carries its `headers`.)

| Header | Exact format |
|---|---|
| `NightMail-Timestamp` | Unix seconds in strict decimal: `0` or `[1-9][0-9]*`, no sign, no leading zeros, no spaces, at most 2^53 − 1 |
| `NightMail-Nonce` | 32 lowercase hex digits (16 bytes) |
| `NightMail-Signature` | 128 lowercase hex digits (64 bytes) |

A header that is missing, repeated, or not exactly in this format makes the request fail (`rejectedHeaders[]`). Header names are case-insensitive.

Where each field of the signed message comes from:

| Field | Client (signs) | Server (verifies) |
|---|---|---|
| `host` | authority of the base URL it has configured | authority of **its own** configured base URL; **never** the `Host` header |
| `version` | the one in the path: `/v1/…` → 1 | the one in the route it served |
| `method` | the request's, in uppercase | `req.method` |
| `path` | the target it sends, with the query | the raw target from `node:http` (`req.url`), without decoding `%xx` or resolving anything. With Express it would be `req.originalUrl`, not `req.url` or `req.path`, which a router may have trimmed |
| `addrKey` | the address's own | the one in the path (`/v1/box/<64 lowercase hex digits>/…`): so the signed key and the path key are the same by construction |
| `timestamp`, `nonce` | the ones it puts in the headers | the ones in the headers |

**`host` = authority of the base URL.** It is the lowercase host name (IPv6 in brackets) plus `:port` **only if the port is not the scheme's default** (80 for `http`, 443 for `https`). In JavaScript it is `URL.host`. In Rust it is `host_str()` plus `port()` from the `url` crate (`port()` returns `None` for the default port).

Examples in `hosts[]`:

- `http://NightMail.Local:80/` → `nightmail.local`
- `http://127.0.0.1:8080` → `127.0.0.1:8080`
- `https://[::1]:8443/` → `[::1]:8443`

Client and server each compute it from their own configuration. If they do not match, the signature does not verify. The result must also meet the `host` rule. A base URL such as `http://mail_server:8080` is a valid URL, but its authority cannot be signed, so it is rejected at startup (`rejectedBaseUrls[]`).

### 2.3 Full authentication (server)

In this order (`authenticateRequest` in `packages/core-ts`):

1. **Time window**: `|now − timestamp| ≤ 60 s`, bounds included (`timeWindow[]`).
2. **Signature** (2.1). Nothing is stored up to this point: someone without the key cannot fill the store or use up other people's nonces.
3. **Nonce**: check and insert `(addrKey, nonce)` in a single atomic step. If it was already there, it is a replay.

**The nonce is remembered until `timestamp + 60 s` (inclusive)**, not for 60 s from the moment the request arrived. A request signed with a clock 60 s ahead is still inside the window 120 s after it arrives. The nonce can only be forgotten when `now > timestamp + 60`.

**Restarts.** If the nonce store is in memory, it is lost on restart. In that case every request with `timestamp ≤ startup + 60` is rejected: those are the requests that may have been seen before the restart. This does not depend on anyone remembering to do it. The store declares since when it remembers (`NonceStore.startedAt`). `MemoryNonceStore` requires the startup time when it is created, and a persistent store declares `null`. `authenticateRequest` reads it from there. The cost: during the first 60 s after startup, legitimate requests are rejected and the client retries.

To the outside, the three rejections give the same response (401, with the `Date` header). The reason only goes to the server logs.

### 2.4 Client clock (privacy)

The signed `timestamp` reveals the offset of the device clock. That offset is the same for all of a user's addresses, so it would be enough to link them. This is why **the client never signs with its raw clock, but with the server time**:

1. **Time per address and per round** (provisional design decision). Before the signed requests of an address in a sync round, the client asks for the time with an unsigned request of its own (`GET /v1/time`). It anchors that time to a **monotonic clock** (the instant the response arrived). Without that time it signs nothing. The time is not shared between addresses. A common difference from the local clock (and its sub-second phase) would be an identifier that would link the addresses, and the server could even choose it.
2. It signs with `server time + time elapsed since the anchor` (monotonic clock, in whole seconds). Never with the raw local clock.
3. If a request is rejected, the client takes the `Date` of the response as the new time for **that address** (or asks `/v1/time` again if there is no `Date`). It then retries **once only**, with a fresh nonce. If that fails too, it does not insist. It waits for a growing interval (for example 1 s, 2 s, 4 s… up to a cap) before trying again, so that a rejection does not turn into a recognisable burst. A time outside the signable range (above 2^53 − 1) is rejected.

### 2.5 What is in `request-auth.json`

- `auth`: the address key of all vectors.
- `valid[]`: `request` → `message` (the signed bytes), `signature` and `headers`. The Rust core must reproduce **all three** with `auth.secretKey`. It includes the longest path (2048 characters).
- `invalid[]`: `authPublicKey` + `request` + `signature` that verification **must reject**: altered signature, signature of another request (one field changed each time), another key, wrong lengths, non-canonical `S` and low-order keys.
- `rejectedRequests[]`: requests that are not in canonical form. `field` says which field. Some of them (negative timestamp, or one with decimals) only make sense for an untyped implementation.
- `rejectedHeaders[]`: header values (`header`, `value`) that the server rejects, changing one at a time in the headers of the first valid vector.
- `hosts[]`: `baseUrl` → `host`. `rejectedBaseUrls[]`: base URLs that do not give a signable `host`.
- `timeWindow[]`: `timestamp`, `now`, `toleranceSeconds` → `accepted`.

Notes for Rust (checked with `ed25519-dalek` 2.2.0 and `url` 2.5.8):

- `SigningKey::from_bytes(&[u8; 32])` and `sign` reproduce `signature`.
- `Url::host_str()` plus `Url::port()` reproduce `hosts`.
- If it ever verifies, `VerifyingKey::verify_strict` rejects every `invalid` vector, low-order keys included.

## 3. App keys: derivation, seed file and `nameCipher`

All of this is local to the app (the Rust core, `apps/desktop/src-tauri/src/keys.rs` and `apps/desktop/src-tauri/src/crypto.rs`). The server never sees it. The vectors make sure that a change of crate or of code does not silently change a user's keys. A different key for the same phrase is a lost account.

### 3.1 Phrase and `master`

- **24-word English BIP39** phrase (256 bits of entropy + 8 checksum bits). On restore, the checksum and exactly 24 words are required. Uppercase is accepted: the phrase is converted to ASCII lowercase before the check (provisional design decision).
- `master` = BIP39 seed = `PBKDF2-HMAC-SHA512(NFKD phrase, "mnemonic", 2048 iterations, 64 bytes)` (empty passphrase).

### 3.2 Derivation

```
derive(label) = HKDF-SHA256(ikm = master (64),
                            salt = empty,
                            info = "nightmail/v1/" ‖ label   (ASCII),
                            L = 32)
```

A bono is a plan voucher (free or paid) that holds a set of address slots. `bono/<n>` is only its key-derivation label.

`n` = bono number (`u32`), `j` = slot number (`u8`), both in decimal without leading zeros. `kind` ∈ `mailbox` | `alias`.

| Label | Use |
|---|---|
| `bono/<n>` | `s` of bono `n` |
| `addr/<n>/<kind>/<j>/enc` | X25519 secret key of the address in slot (n, kind, j); its public key is `encPk` |
| `addr/<n>/<kind>/<j>/auth` | Ed25519 seed (RFC 8032) of that address; its public key is `authPk` |
| `salt/<n>/mailbox/<j>` | `salt` of the former `reserveMailbox` commitment (unused since the one-step `registerMailbox`, 2026-11-27) |
| `names` | XChaCha20-Poly1305 key of `nameCipher` (3.4) |
| `wallet` | seed of the embedded wallet (`wallet.open.seed`) |
| `wallet-state` | `stateKey` of the encrypted wallet state (`wallet.open.stateKey`) |
| `db` | SQLCipher key |

- `id_k` of the bono is not a label. The helper process computes it from `s` and `k`.
- Address keys are per slot and are never derived from `s`. This way `Recovery` can derive them again and check that the registered ones are its own.
- The core has no public `derive(text)` function. Each label has its own method.
- **Phase 2:** the labels do not carry the slot generation (`gen`, currently always 0). If slots are recycled (a later phase), the address of a recycled slot needs another label (for example `addr/<n>/<kind>/<j>/<gen>/enc` for `gen > 0`), without changing the labels for `gen = 0`.

### 3.3 Seed file (`seed.v1`)

JSON on one line, without spaces, with the fields in this order:

```
{"version":1,"kdf":"argon2id","m":65536,"t":3,"p":1,"salt":"<hex 16>","nonce":"<hex 12>","ciphertext":"<hex 48>"}
```

```
key        = Argon2id v1.3 (password in UTF-8 normalised to NFC, salt, m KiB, t passes, p lanes, 32 bytes)
params     = the JSON above without "ciphertext":  {"version":1,"kdf":"argon2id","m":…,"t":…,"p":…,"salt":"…","nonce":"…"}
AAD        = "nightmail:seed-file:v1" ‖ params        (ASCII)
ciphertext = AES-256-GCM(key, nonce, AAD, entropy (32)) ‖ tag (16)
```

- The **entropy** is encrypted, not the words. `salt` and `nonce` are random on every write.
- It is written with m = 65536 (64 MiB), t = 3, p = 1. On open, `m < 19456` or `t < 2` are rejected (OWASP minimums for Argon2id). So are absurd values: `m > 262144` (256 MiB), `t > 16`, and `p` outside 1–16.
- **Only the canonical form opens.** The file must be, byte for byte, the one that would be written with those values: no spaces or final newline, fields in that order, no repeated or extra fields, lowercase hex, `version` 1, `kdf` `argon2id`. A file larger than 1024 bytes, or with bytes that are not UTF-8, does not open either.
- The password is normalised to **NFC** before Argon2id (provisional design decision). The same password written in another Unicode form (for example `ñ` as `n` + combining tilde) opens the same way. Vector: `seedFiles[].equivalentPasswords`.
- A wrong password, an altered or malformed file, and parameters outside the limits all give **the same error**. An empty password is not accepted on creation.
- Disk:
  - Folder 0700 and file 0600.
  - Atomic and exclusive write: temporary file 0600 + `fsync`, `link` to the final name (it fails if that name already exists: creating or restoring **never overwrites** a seed), delete the temporary file, and `fsync` the folder.
  - After the `link` the seed is complete and synced. If deleting the temporary file or the folder `fsync` fails, the write still counts as done (it is not undone).
  - Leftover temporary files older than 60 s are swept on creation.
- On open, the file cannot be a symbolic link, and its permissions cannot be more open than 0600. This gives its own error ("not private"). It is not silently corrected.

### 3.4 `nameCipher` (`nightmail:name-cipher:v1`)

```
nameCipher (104) = nonce (24) ‖ ciphertext (64) ‖ tag (16)
plaintext        = normalised name in UTF-8 ‖ 0x00 … up to 64 bytes
encryption       = XChaCha20-Poly1305(key = derive("names"), random nonce,
                                      AAD = "nightmail:name-cipher:v1" (24 ASCII bytes) ‖ slotNul (32))
```

- The name is the one returned by `contract.hashes` op `normalizeName`: 1–64 bytes of UTF-8 without NUL. Anything else is not sealed.
- Opening: decrypt, remove the trailing zeros, and require 1–64 bytes of valid UTF-8 without NUL. Every rejection is the same error.
- `slotNul` in the AAD binds the name to its slot. Copying the `nameCipher` of another address does not give a valid name.
- For an alias the field is **104 zero bytes**. It does not open (it gives the error).

### 3.5 What is in `keys.json` and `name-cipher.json`

They are generated by `gen-keys.mjs`:

- Run `node packages/test-vectors/crypto/gen-keys.mjs` from the repository root, with Node ≥ 24.7. With `--check` it writes nothing and exits with 1 if the stored files do not match.
- It uses only `node:crypto` (`pbkdf2Sync`, `hkdfSync`, `argon2Sync`, AES-256-GCM, `chacha20-poly1305`, X25519 and Ed25519 through PKCS#8), plus the word list from `@scure/bip39`. The phrase and its checksum are computed in the script. The package is resolved from `packages/midnight`, which declares it.
- XChaCha20 is built from HChaCha20, written in the script (checked against the draft-irtf-cfrg-xchacha §2.2.1 vector), plus `chacha20-poly1305` with the nonce `0⁴ ‖ nonce[16..24]`.
- The starting phrases are official BIP39 vectors (Trezor). Before using them, the script checks the seed of one of them with the passphrase `TREZOR`.

Contents:

- `keys.json`:
  - `phrases[]`: `entropy` → `phrase` → `seed` (= `master`).
  - `derivation`: with the phrase `legal winner … title`: `bono[]` (`n`), `mailboxSalt[]` (`n`, `j`), `fixed` (`names`, `wallet`, `walletState`, `db`) and `addresses[]` (`n`, `kind`, `j`, and in `enc` and `auth` the output and its `publicKey`). Each output carries `label`, `info` and `okm`.
  - `seedFiles[]`: `password`, `equivalentPasswords` (other Unicode forms that open the same way: NFD), `nonEquivalentPasswords` (the NFKC form, which does NOT open: `ª` → `a`; this tells NFC from NFKC), `entropy`, `phrase`, the Argon2id key (`key`), the `aad` and the whole file (`file`). They use the minimums (m = 19456, t = 2), so they open under the real policy.
  - `constants`: label prefix, file domain, Argon2id minimums and maximums, and maximum file size.
- `name-cipher.json`: `key`, `slotNul`, `names[]` (`name`, `nonce` → `nameCipher`), `openFailures[]` and `sealFailures`.
  - `openFailures[]`: altered nonce, ciphertext or tag; another `slotNul`; an alias of 104 zero bytes; and, with a valid tag: empty name, NUL inside, invalid or truncated UTF-8.
  - `sealFailures`: 65 bytes, empty, with NUL.

The Rust core must:

- reproduce `phrases` in both directions;
- reproduce every output of `derivation` **with its typed API** (and check that the label is the one in the vector);
- open `seedFiles` and reproduce `file` byte for byte with its `salt` and `nonce`;
- seal `names` with the given nonce and open them;
- reject `openFailures` and `sealFailures`.

### 3.6 Known memory limits

The core keeps every secret of its own in buffers that are wiped when dropped (`zeroize`). This covers:

- `master` (on the heap, so that moving the `KeyManager` leaves no copies);
- entropy;
- the phrase (allocated once, never reallocated);
- the normalised password;
- the Argon2id working memory (fallible allocation);
- derived keys.

The following are outside its reach, and are accepted in the MVP:

- Internal copies in the crates that are not wiped: `bip39`'s PBKDF2 (the phrase and HMAC-SHA512 states), `hkdf`'s HMAC states, the NFKD normalisation of the phrase (`parse_in` makes a copy) and the NFC normalisation of the password while iterating.
- Internal cipher state that is not wiped on drop: the GHASH hash key `H` (AES-GCM; `polyval` keeps it in a `ManuallyDrop`) and the per-message Poly1305 key (`nameCipher`). They only authenticate, they do not decrypt.
- Memory is not locked (`mlock`/`VirtualLock`). A secret can end up in the swap file or in a dump.
- Whatever the interface and the Tauri bridge do with the password and the phrase before they reach the core.

## 4. End-to-end mail between NightMail addresses (`nightmail:e2e`, version 1)

The sending app **signs** the mail with the Ed25519 key of the sending address (the `auth` key of §2, with a different signature domain). It then **seals the whole mail, signature included**, with the envelope of §1, to the recipient's `encPk`. The server only sees one more envelope: same header, same buckets. Anyone can encrypt to a public `encPk`, the server too. So the only proof of who wrote the mail is the signature inside.

Design decisions:

- Normal signature: the recipient can prove to third parties who wrote the mail. It is not deniable.
- One recipient only.
- No attachments.
- The subject is encrypted inside the mail.
- Sent mail is stored locally only.

Implementations: `packages/core-ts/src/mail.ts` (generates the vectors) and `apps/desktop/src-tauri/src/mail/e2e.rs` (the core: sends and verifies).

### 4.1 Format

What goes inside the envelope is `payload ‖ signature`:

| Order | Field | Bytes |
|---|---|---|
| 1 | magic | `"nightmail:e2e"`, 13 ASCII bytes |
| 2 | version | 1 byte, currently `0x01` |
| 3 | `messageId` | 16 random bytes |
| 4 | date | `u64be`, Unix seconds |
| 5 | sender `addrKey` | 32 bytes |
| 6 | sender address | `u8(length)` ‖ ASCII |
| 7 | recipient `addrKey` | 32 bytes |
| 8 | recipient address | `u8(length)` ‖ ASCII |
| 9 | subject | `u16be(length)` ‖ UTF-8 |
| 10 | body | `u32be(length)` ‖ UTF-8 |
| 11 | signature | 64 bytes |

```
payload   = fields 1 to 10
signature = Ed25519(auth seed of the sending address, "nightmail:mail-sig:v1" (21 ASCII bytes) ‖ payload)
envelope  = §1.4 envelope (payload ‖ signature), to the recipient's encPk
```

- **Everything is signed** except the signature itself: magic and version, `messageId`, date, sender and recipient (`addrKey` **and** text), subject and body. Because the recipient is part of what is signed, a mail signed for one address is not valid if someone seals it again for another.
- **Everything is encrypted**, signature included. The server sees neither the subject nor who signs.
- **Separate signature domain.** The signed messages of §2 start with `nightmail:mailbox-api:v1`, and these start with `nightmail:mail-sig:v1`. They differ at byte offset 14 (the 15th byte). So a request signature is never valid as a mail signature, nor the other way round, even with the same key. The magic (`nightmail:e2e`) is another string: it marks the content, not the signature.
- Pure Ed25519 (RFC 8032, deterministic), over the whole message, without prehash.
- Variable-length fields carry their length in front, and the signature is exactly the final 64 bytes. So two different mails never give the same bytes. `encodingExample` in the JSON breaks down the first vector field by field.

### 4.2 Field rules

| Field | Rule |
|---|---|
| `messageId` | exactly 16 bytes |
| date | Unix seconds, integer from 0 to **253402300799** (9999-12-31 23:59:59 UTC). A later date cannot be shown as a normal calendar date |
| address | `local@domain` in lowercase ASCII: local part of 1–64 characters from `a-z 0-9 . _ -`, one `@`, and a domain of 1–190 characters from `a-z 0-9 . -` (255 bytes at most). It is the form `normalizeName` gives, so two addresses are compared byte for byte |
| subject | valid UTF-8 of 0–1024 bytes, a single line: no C0 controls (`0x00`–`0x1f`, line breaks and tab included), no DEL (`0x7f`), no line or paragraph separators (U+2028, U+2029), and no **deceptive characters** (below) |
| body | valid UTF-8, with no limit of its own. Of the C0 controls only tab (`0x09`), line feed (`0x0a`) and carriage return (`0x0d`) are allowed: no NUL, no ESC, none of the rest. No DEL and no **deceptive characters**, except one U+FEFF as the first character (below) |
| total | payload + signature ≤ **26214400 bytes (25 MiB, the same limit as SMTP)**. The fixed part is 174 bytes (`constants.fixedLength`). If the total is exceeded, the field at fault is the body |

**Deceptive characters** (`constants.deceptiveCharacters`) change what is shown without being visible themselves. They are not allowed in the subject or in the body:

| Code points | What they are | Why |
|---|---|---|
| U+0080–U+009F | C1 controls | no use in text; some terminals interpret them (U+009B starts a control sequence) |
| U+061C, U+200E, U+200F | direction marks (ALM, LRM, RLM) | invisible; they change the order in which the surrounding characters are shown |
| U+202A–U+202E | direction embeddings and overrides (LRE, RLE, PDF, LRO, RLO) | U+202E shows `fdp.exe` as `exe.pdf` |
| U+2060–U+206F | word joiner, invisible operators, direction isolates (U+2066–U+2069) and deprecated format characters | invisible; the isolates reorder text like the overrides |
| U+200B | zero-width space | invisible: two different texts look the same |
| U+FEFF | byte order mark / zero-width no-break space | invisible; only allowed as the first character of the body |

Decisions:

- **Rejected, not neutralised.** The format cannot "clean" what was signed without invalidating the signature, and the reader must not show something different from what was signed. The composing app must remove these characters (or warn) **before** signing.
- **U+200C and U+200D (ZWNJ, ZWJ) are allowed.** Persian and the Indic scripts need them, and emoji sequences (👨‍👩‍👧, profession emoji…) are built with U+200D. They do not reorder or hide text. On their own they only change how neighbouring letters join.
- **U+FEFF only at the start of the body**, as before. It is the byte order mark that some editors leave when a file is pasted, and it is kept as is. Anywhere else (and anywhere in the subject) it is the old invisible space, replaced by U+2060, which is not allowed either.
- In the body, LF, CRLF and lone CR line breaks are allowed: they are normal line breaks in a text view. ESC (`0x1b`) and the other C0 controls are rejected: in a terminal or a log they can erase or rewrite what is shown.
- The list covers the most common cases, not all of Unicode. Homoglyphs (a Cyrillic `а` for an `a`) are still possible in the subject and the body. Addresses do not have this problem (ASCII only).

Applying the rules:

- The writer **normalises nothing silently**. Whatever breaks the rules is not signed, and the error names the field, never its value. In TypeScript, a text with a lone UTF-16 surrogate is not accepted either (`TextEncoder` would replace it with U+FFFD).
- The reader applies **the same rules**. UTF-8 is strict: truncated sequences, overlong encodings and encoded surrogates are rejected. A U+FEFF at the start of the body is kept as is (in TypeScript, `TextDecoder` with `ignoreBOM: true`; otherwise it would strip it).

### 4.3 Sending

1. Build the payload with the rules of 4.2.
   - **The date does not simply come from the local clock (mandatory).** It is the server time **of the sending address**, the same time that signs its requests (§2.4). In the core it is the clock of that address's session in `mail::client`: `GET /v1/time` anchored to a monotonic clock, never shared between addresses.
   - The device clock offset is the same for all of a user's addresses, and the recipient would see it in every mail. That would be enough to link them.
   - Without that time nothing is sent, just as §2.4 signs no request without it.
   - This does not change the format. It is a rule for the sender, and the recipient cannot check it.
2. Sign with the auth seed of the sending address.
3. Seal `payload ‖ signature` as in §1.4, with a fresh ephemeral key and nonce. An `encPk` that is not usable (§1.2: canonical and not low order) is rejected before signing.

### 4.4 Opening and verifying the sender

1. Open the envelope (§1.5). If the plaintext does not start with the magic, it is a normal MIME mail (what arrives over SMTP).
2. **Decode**, in this order:
   - the 25 MiB limit, before anything else;
   - the magic;
   - version `0x01` (any other is not read);
   - each field, with its length and its rules;
   - the signature takes exactly what is left (64 bytes, not one more or one less).

   Any failure gives **the same error** (`invalid mail`), without saying which.
3. **Verify.** If any of the following fails, it is not an error. The mail is returned with **sender verified = no** and the address it claims to be from:
   1. The signed recipient (`addrKey` and text) is **this** address. If it is not, stop here (do not even look up the sender).
   2. The sender's auth key comes **from the chain, not from the mail**. The caller supplies a function (the *resolver*). It receives the declared `addrKey` and text, and answers one of three things:
      - **the `authPk`**, only if the full text resolves to that same `addrKey` with **the same resolution used when sending** (in the core, `resolve_recipient`):
        - the domain is **exactly the configured one** (another domain is not a NightMail address, even if the local part matches);
        - a local part shaped like an alias is looked up only as an alias, by its full text (words and suffix);
        - any other local part is looked up as a mailbox by `H(name)`, and only if that record is a mailbox;
        - reserved names never resolve;
        - at the end, **the `addrKey` and the text are compared byte for byte** with the ones found.

        Checking only the local part would accept `name@other.domain` signed with the real key (an `unverified` vector with another domain).
      - **"no"** (any other answer): sender verified = no.
      - **"cannot answer now"** (the registry cannot be read, or is not recent enough). This is **not** "not verified". Opening gives its own error (`SenderUnavailable` in Rust, `MailOpenError` with code `sender-unavailable` in TypeScript). The receiver keeps the envelope and tries again later. A transient failure must not mark a good mail as doubtful forever.

      The signature proves who holds the key, not that the text belongs to them. Looking up the registry is asynchronous and the resolver is not, so the flow is:
      1. open the envelope;
      2. **extract the declared sender** (`declared_sender` / `declaredSender`: format only, without checking the signature; never for display);
      3. look it up in the registry (`resolve_sender`);
      4. verify with that answer (`sender_resolver` / `senderResolverFor` and `open_mail` / `openMail`).
   3. The key is usable (`isUsableAuthPublicKey`, §2.1), and the signature is valid under the rules of `ed25519-dalek`'s `verify_strict`: canonical `S`, `R` compared byte for byte, and neither `R` nor the key of low order.
      - OpenSSL does not reject a low-order `R`. A key holder can build a signature with `R` = identity that OpenSSL accepts. The TypeScript version adds that check to give the same verdict as Rust.
      - Both check **without the cofactor** (`S·B = R + k·A`). Take a key with a small-order component (`A = a·B + T`, `T` of order 8; it is usable because it is not low order). A signature by its owner is valid only if 8 divides `k`, the same on both sides (vectors `mixedOrderKey`).
      - A verifier **with** the cofactor would accept all of them. Another implementation must verify without it to give the same verdict.
4. **Result**: `messageId`, date, sender (`addrKey` and text) with **sender verified: yes/no**, recipient, subject and body. As "From", only the verified address may be shown as genuine, never unverified text from the mail.
   - **The date is unverified data**, even when the sender is verified. The signature only says the sender wrote that number. The interface **shows and sorts by arrival time** (the download time, or the one the server stores), never by the mail date. If it shows the mail date, it is as secondary information.

The receiver keeps a single mail per (sender `addrKey`, `messageId`): the server may deliver a copy again.

### 4.5 What is in `e2e-mail.json`

- `constants`: magic, version, signature domain, lengths, limits and `deceptiveCharacters` (`[first, last]` ranges from 4.2). Both sides check their subject and body rules against this list, code point by code point.
- `sender` (`authSecretKey`, `authPublicKey`, `addrKey`, `address`) and `recipient` (`encSecretKey`, `encPublicKey`, `addrKey`, `address`).
- `directory[]`: what the chain would say (`addrKey`, `address`, `authPublicKey`). It holds:
  - the sender;
  - another registered address;
  - the sender address used by the longest-address vector (same key as the sender);
  - an address with the low-order key `01 00 … 00`;
  - another one (`mixta@…`) with a mixed-component key (`a·B + T`, `T` of order 8).

  The tests look up by `addrKey` **and** full text (domain included), as the resolver of 4.4 must. The core's resolver (`resolve_sender`) is also tested with this same directory registered in a test registry.
- `encodingExample`: the first vector, field by field (with its length prefix).
- `valid[]`: `mail` → `payload` (or only `payloadSha256` and `payloadLength`), `signature` and, with `ephemeralSecretKey` and `nonce`, the envelope (in full in `envelope` except for the large one; `envelopeLength` and `envelopeSha256` always).
  - A large body is given as `bodyPattern` + `bodyLength`: **byte `i` is `a` + `i mod 26`**.
  - The vectors cover: empty subject and body; accents, emoji and mixed line breaks; a body starting with U+FEFF; U+200D in an emoji and U+200C in Persian (allowed) with a lone CR in the body; the longest subject (1024 bytes: 512 × `ñ`); the longest addresses; date 0; the maximum date (253402300799); and the largest mail (exactly 25 MiB).
- `unverified[]`: `plaintext` that decodes but gives **sender verified = no**, and the `mail` it must return. Cases:
  - altered signature (in `R` and in `S`);
  - subject changed after signing;
  - signed for another recipient (`addrKey`, text, or both);
  - forged sender (claims to be another registered address);
  - sender not in the registry;
  - sender `addrKey` with another address's text;
  - the sender's alias `addrKey` and text but **in another domain** (`…@otro.example`, signed with its real key: the core test checks that `resolve_sender` rejects it);
  - signed with another key;
  - signed with the request domain;
  - signed without a domain;
  - non-canonical `S`;
  - `R` = identity made by the key owner;
  - the same with `R` = identity written another way (`y = p + 1`, non-canonical, and with the sign bit set: a verifier that decoded `R` and compared points would accept them);
  - low-order key with the trivial signature.

  The generator checks that a plain Ed25519 verifier with no extra rules (OpenSSL) accepts the canonical `R` = identity and the trivial signature. Otherwise those vectors would prove nothing.
- `mixedOrderKey[]`: mails from the address with the mixed-component key, with `plaintext`, `mail` and the expected `senderVerified`. One has `k` a multiple of 8 (**yes**) and another does not (**no**; with the cofactor it would be accepted). The generator checks that OpenSSL gives the same verdict.
- `openFailures[]`: `plaintext` that must give the error:
  - empty, magic only, another magic;
  - versions `0x02` and `0x00`;
  - truncated (without the last byte, without signature, cut inside the body);
  - one byte too many;
  - lengths that run past the end of the text;
  - malformed addresses;
  - a subject of 1025 bytes, with a line break or with DEL;
  - invalid UTF-8 in the subject or the body;
  - NUL in the body;
  - deceptive characters (U+202E or a C1 control in the subject, a subject starting with U+FEFF; ESC, DEL, U+2067, U+200B, or a U+FEFF that is not the first one, in the body);
  - dates 253402300800 (one second after the maximum), 2^53 and 2^64 − 1.

  Entries marked `signed` carry a valid signature: they are rejected for their format, not for the signature.
- `openFailureOversized`: a well-formed, signed mail of 25 MiB + 1 byte. It is not stored in full. Rebuild it with `bodyPattern` and `bodyLength`, and compare it with `plaintextSha256`.
- `encodeFailures[]`: `mail` + `field`: mails that must not be buildable, and the field that prevents it. They include one example of each group of deceptive characters in the subject and in the body, and the C0 controls of the body (ESC, BEL, vertical tab, form feed). Some of them (a 15-byte identifier, a negative date or one with decimals, a 31-byte `addrKey`) only make sense for an untyped implementation.

The Rust core must:

- reproduce `payload`, `signature` and the envelope of each `valid` entry (sealing with the given ephemeral key and nonce), open them and verify the sender;
- give sender not verified for `unverified`, and the stored verdict for `mixedOrderKey`, with the expected `mail`;
- reject `openFailures` and `openFailureOversized`;
- refuse to build `encodeFailures`, for that same field.

Since both sides produce exactly the same bytes, what one side seals the other opens and verifies.

### 4.6 Known limits

- **Provable signature** (design decision): the recipient can prove to third parties that the sending address wrote that mail. A deniable authentication (such as HPKE's Auth mode) would not allow this.
- The `auth` key signs both requests and mails. The separation relies only on the different domains. A separate mail signing key would have to be published in the contract.
- No forward secrecy and no post-quantum protection, same as §1.
- The sender sets the date and nobody checks it (this is why the interface sorts by arrival time, 4.4). Someone sending with another app can put any date, including their raw clock. The rule in 4.3 protects people who use NightMail.
- **Domain change** (from `nightmail.local`, the one used for local testing and in these vectors, to the real domain at deployment):
  - The domain is **inside what is signed**, in the sender text and in the recipient text.
  - A mail signed with the old domain and opened after the change comes out with **sender verified = no**, for two reasons: the signed recipient is no longer "this" address (4.4.3.1), and the resolver only accepts the configured domain (4.4.3.2).
  - So the verification result must be stored on receipt and not recomputed on display. The domain change must happen before there is real mail between NightMail addresses.
  - Accepting both domains for a while would require changing the resolver and the recipient comparison. This is not done today.
- The verification is only as good as the function of 4.4. If the indexer lies about the `authPk`, the verified sender lies too.
- A mail arriving over SMTP can start with the magic on purpose. Without the sender's key it cannot come out verified. But the reader has to decide what to do with a mail that starts with the magic and does not decode (for example, not show it as e2e).
